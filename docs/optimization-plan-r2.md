## 1. 现状审计（代码 + 实况）

### 1.1 ① 音轨是否单轨 —— 三层确认：全是单轨

| 层 | 证据 | 结论 |
|---|---|---|
| 数据模型 | `js/model.js` L44：`timeline.audioClips: []` 扁平数组；clip 结构（L458-497）**无 trackId 字段**；`media.assets[]` 支持多资产，但 clip 全部落在同一条逻辑轨 | 单轨（多资产≠多轨） |
| 渲染 | `js/timeline.js` `drawAudioLane`（L364-477）只画一条 lane（`audioTop/audioLaneH`），所有 clip 按数组序画在同一道内（z 序=数组序）；轨表头 `#tl-head` 仅一份（120px：资产名/时长/音量/静音） | 单 lane |
| 引擎 | `js/audio-clips.js` `ClipTransport`（L323-468）：单 `master` GainNode、单 `trackGainVal/trackMuted`；`computeOverlaps/applyAutoCrossfades/rippleDeleteClips/effectiveRegions` 全部按扁平数组计算，无轨作用域 | 单输出链、单轨语义 |

多资产能力已就位（媒体库多文件导入、clip 可引用任意 asset、拖资产入轨落点生成 clip），**缺的只是「轨」这一层容器**——这决定了 §3.1 方案是「加一层」而不是「重写」。

### 1.2 ② 展开态与队形块区的关系 —— 同屏共存，无模式切换

实测几何（探针 `r2-c`，1360×860）：

| 态 | 音频 lane | 块区 top | 总高 | 块区可见 |
|---|---|---|---|---|
| 简单态 | 26px（top 40-66） | 72px | 150px | 是 |
| 展开态 | 72px（top 40-112） | 118px | 160px | **是（blocksVisibleInRange=true）** |

- `js/timeline.js` L289-301：`blocksTopFor() = audioBottom() + 6`——展开态只是把块区往下推 6px，**从不隐藏**；`totalHeightFor()` 展开态按内容 160px 收纳。
- 实况截图：`out/round45-r2/r2-a-expanded.png`——波形轨与队形块区同屏，变速点后波形变密而小节刻度依旧均匀（§2.1 漂移的肉眼证据）。
- 展开态记忆 `localStorage('wuzhen:audioTrackExpanded')`；无任何「隐藏队形信息」的形态。

用户要的「展开后隐藏队形块区、只留 tag」在现实现中不存在 → §3.2 双 UI 模式方案。

### 1.3 ③ 节拍体系的实现与限制

**模型（`js/model.js`）**：
- `spb = 60 / bpm`（L282）；`beatToSec = firstBeatSec + beat × spb`（L283）；`secToBeat` 反解（L284）——**单值 BPM + 固定首拍的线性模型**，无分段、无渐变。
- `blocks[]`：`holdBeats/travelBeats`（L275-281，syncTimeline 默认 16/8）；`computeSegments` 全按拍累加。
- `tags[]`：`{id, beat, name}` 纯拍位标记（L311-363）。
- 换算收敛性好：**beatToSec/secToBeat 共 46 个调用点**（timeline.js×24、player.js×11、main.js×7、model.js×4），`spb(` 直接调用仅 6 处（timeline×4：标尺/块标签/微移网格；player×1：数拍间隔；main×1：块秒数显示）——这给 §2.3 方案 C（节奏图）留了低成本接入面。

**依赖拍模型的用户可见面**：
1. 标尺：小节刻度（`beatToSec(bar×bpb)`）+ 8 拍刻度（`timeline.js` L494-511）；
2. 队形块区：块边界、徽标「16拍·8s」、过渡标签；
3. tag 旗点定位与拖拽；
4. 播放头：`beat = secToBeat(audio.currentTime)` 反推（`player.js` L227-233）；
5. 节拍器：整拍触发（L237-245）；数拍入场：`interval = spb×1000/speed` 定频 setInterval（L85-107）；
6. 块吸附：拖块边自动吸整拍（`timeline.js` L1213-1216）；clip 微移 Shift 网格 = `spb`（L1377）；
7. 「按队形段自动切」：块边界（拍）→秒（`main.js` L1360-1368）；
8. 对齐工具：BPM 输入/点拍/首拍/「对齐到播放头」（单值假设的校准入口）。

**限制（一句话）**：拍↔秒换算仅在「全曲恒定 BPM」时成立；变速曲（现场版/渐快渐慢/多段 BPM）下拍线、tag、块边界、节拍器、数拍全部漂移——漂移量级见 §2.1 实证。

## 2. 实证研究（重点=反馈 #3）

### 2.1 实证 A：变速音乐下「拍↔秒对齐」可靠性 —— 钉死：不可靠

**方法**：Node 合成 60s 变速 click 曲（0-30s @120BPM、30-60s @160BPM，140 个乐拍，accent 每 4 拍）→ 经真实 UI 路径（`#audio-file` input）载入 WuZhen → 设单值 BPM=120、首拍=0（该模型的默认口径）→ 从解码 buffer 实测 140 个 onset，用**应用自己的 `beatToSec/secToBeat`** 度量每个乐拍与拍线的偏移。

**偏移曲线（实测，`out/round45-r2/r2-a-drift-curve.json`）**：

| 乐拍 | 实际发生时刻 | 拍线位置（应用绘制） | 偏移 |
|---|---|---|---|
| 0 / 30 / 59 / 60 | 0 / 15 / 29.5 / 30s | 同左 | **0（前半段完全对齐）** |
| 70 | 33.75s | 35s | −1.25s（−2.5 拍） |
| 80 | 37.5s | 40s | −2.5s（−5 拍） |
| 90 | 41.25s | 45s | −3.75s（−7.5 拍） |
| **100** | **45s** | **50s** | **−5s（−10 拍）** |
| 120 | 52.5s | 60s | −7.5s（−15 拍） |
| 139 | 59.625s | 69.5s | **−9.875s（−19.75 拍）** |

**统计**：

| 段 | 乐拍数 | 落在拍线上（±60ms） | 最大偏移 | 平均偏移 |
|---|---|---|---|---|
| 前半 120BPM（模型吻合） | 60 | **100%** | 0 | 0 |
| 后半 160BPM（节奏型变化） | 80 | **1（1.25%）** | **9.875s / 19.75 拍** | 4.938s |

**最佳拟合反证**：对全部 140 拍做最小二乘回归得 BPM=140.51——两段各自仍偏，最大残差 **4.378s**。**结论：单值 BPM 无法用「调准一点」救回变速曲，任何折中都是两段都错。**

**UI 后果（同探针实测）**：
- tag@beat100 画在 50s，而 beat-100 的乐音实际在 45s 响——**标记晚 5 秒**；
- 块边界（队形 5 起点=beat 96）画在 48s，实际乐拍 96 在 43.5s——**换形点晚 4.5 秒**；
- 节拍器实测：从 grid beat 80（t=40s，该时刻实际乐拍已是 86.67）带节拍器播放 3s，节拍器按 0.5s 网格响 5 声，而音乐实际乐拍以 0.375s 间隔流过 8 拍——**节拍器与音乐即刻脱拍，且相位持续漂移**；播放头停时标称 beat 85.98，实际乐拍 94.6+。

**边界结论（回答「快速对齐 clip 与节拍的能力目前是否可靠」）**：
- 对**恒速曲**：可靠（前半段 100% on-grid；round30 亦证 scrub/变速播放 playbackRate 拍点对齐）；
- 对**节奏型变化/分段 BPM 曲**：系统性失效，偏移线性累积、无自愈路径；
- 对**无节奏型音乐**（氛围/管弦）：拍线本身无锚，属「无意义呈现」而非「错误」——需降级策略（§3.3）。

### 2.2 实证 B：clip 引擎在变速音乐下的秒制免疫性 —— 钉死：免疫

**Node 层**（`js/audio-clips.js` 纯函数直测，BPM=120 与 240 两组项目执行同一操作序列）：
- 分割@30s → 左缘内容锚定 trim→32s → 波纹删除：**两组结果逐字段完全一致**（`r2-b-clip-immune.json.node.identical=true`）；
- 静态证据：`audio-clips.js` 的 import 仅 `{ uid, MIN_CLIP_DUR }`，引擎源码中 `bpm/beatToSec/secToBeat/spb(` 引用计数 = **0**。clip 四元组 `{timelineStartSec, srcStartSec, lengthSec, fade×2}` 全秒制。

**应用层**（真实 UI 路径）：
- 播放头分割@变速点 t=30s：`splitBoundary=30`（秒制精确落点）；分割后把 BPM 120→240：**clip 数据逐字节不变**；
- ClipTransport 起播@45s，1.5s 后 position=46.509s（player beat 93=46.5×2@120）——调度域纯秒；
- 「按队形段自动切」边界落点：BPM120 下前 3 边界 [12,24,36]s，BPM240 下 [6,12,18]s——**切割引擎忠实于输入秒值，但输入来自拍模型**（垃圾进垃圾出：拍线错了切点就错）。

**两处例外（clip 操作中仅有的拍耦合面）**：
1. `nudgeSelected(grid=true)`（Shift+←/→ 整拍微移）：步长 = `spb`（实测 0.5s@120 / 0.25s@240）；
2. 「按队形段自动切」的边界来源 = `beatToSec(块边界)`。

**结论**：用户反馈「放弃节奏和 clip 的节拍绑定」——**该绑定本来就不存在**。clip 层对节奏型天然免疫，无需任何改动；唯一要修的是上述两处的输入语义（§3.3）。

### 2.3 时间轴基座三方案复杂度对比

| 维度 | A·恒定 BPM 拍制（现状） | B·秒制时间轴（块以秒定位，BPM 仅显示） | C·有限节奏图（分段 BPM 表） |
|---|---|---|---|
| 数据模型 | 不动 | `blocks.holdBeats/travelBeats` → `holdSec/travelSec`（或并存双字段）；tags `beat`→`sec`；项目格式升 version，**存量迁移全量** | 新增 `audio.tempoMap?: [{fromBeat, bpm}]`（缺省=恒定，向后兼容零迁移）；blocks/tags 仍拍制 |
| `beatToSec/secToBeat` | 线性（46 调用点不变） | 队形链路全部改秒（46 点大半重写）；clip 链路不动 | 改 3 个函数为分段线性（二分查段），**46 个调用点签名不变自动受益** |
| `spb(` 6 处直调 | 不动 | 删除/替换 | → `spbAt(project, beat)`（带拍上下文）：标尺、微移网格、数拍间隔、块标签 4 处需逐拍化 |
| blocks/tags/skill 冲击 | 无 | **最大**：块时长栏/±步进/拖边吸整拍/属性面板/`alignBlockStart`/`computeSegments`/说明书/导出格式/既有 232+ 单测与全套 E2E 断言口径全动 | 无（块仍按拍编排；仅换算精度提升） |
| 数拍/节拍器 | 恒速曲正确；变速曲漂移（§2.1） | 语义崩（拍不再是一等公民，数拍需另建拍层） | 分段间隔可精确（数拍 interval 逐拍查表） |
| 用户心智 | 编舞「16 拍/八拍」直给（领域母语） | 变成「16 秒」——**丢掉八拍语义**，与教学/排练习惯冲突 | 保持八拍语义 + 承认变速 |
| 变速曲对齐 | ❌ 漂移至秒级/十拍级（实证） | ✅ 天然免疫 | ✅ 修正（限分段恒速；渐变仍近似） |
| 工作量 | S（文档化+显性化） | **L**（近似重写队形时间轴层） | **M**（3 函数 + 4 直调点 + tempoMap 编辑 UI） |
| 风险 | 变速曲错位被用户当 bug 报 | 回归面巨大、领域语义受损 | tempoMap 编辑 UX 复杂度；渐变速仍近似 |
| 先例 | — | lightmix（其域内**本就没有拍概念**，时间轴=pps+NICE_STEPS 秒网格+SMPTE，见 §2.4） | DAW 通用做法（Audition/Reaper tempo map） |

**裁定倾向（详见 §3.3）**：剪辑层维持秒制（已成立）；队形层**不采用 B**（丢八拍语义+回归面不可控）；**P0=A 的显性化+降级**，**P1=按需上 C**。lightmix 的秒制经验证明 B 在「纯音乐域」是正解，但 WuZhen 时间轴同时承载队形块（领域拍值），B 的先例不可直接平移。

### 2.4 lightmix 参照（B 方案可行性的边界注记）

- `src/core/model.ts`：`Session { tracks: Track[] }`、`Track { id, name, volumeDb, pan, mute, solo, height, clips[] }`、`Clip { assetId, trackId, start, duration, offset, gainDb, fadeIn/Out, stretch? }`——**多轨=轨容器+clip.trackId**，clip 仍扁平语义（z 序=数组序、越后越上层）。
- `src/core/time.ts`：`Viewport { pps, scrollSec }`、标尺刻度 `NICE_STEPS`（0.001…3600 秒族）+ `formatTime(decimal|SMPTE)`——**全文件无 beat/bar 概念**。lightmix 的「秒制可行」先例成立域=纯音频工程；它没有队形、没有八拍、没有任何需要拍值的领域对象。
- 可直接借用的实现细节：`effectiveMute`（solo 派生静音）、`insertAsset` 冲突顺延落点、`audibleRegions` z 序出声、ripple 按轨分组平移（`rippleDelete` 的 byTrack Map）——§3.1 多轨语义照抄点。

### 3.1 真·多轨（反馈 #1）—— P1

**数据模型（最小增量，lightmix 对齐点）**：
```
project.timeline.trackList = [ { id:'trk1', name:'音轨 1', gain:1, muted:false, height:72 } ]   // 新增
project.timeline.audioClips[i].trackId = 'trk1'                                                // clip 增列（缺省 trk1）
```
- 不学 lightmix 把 clips 嵌进 track：WuZhen 已发运扁平 `audioClips`，保扁平 + trackId 使 `clipsOf()/sanitizeAudioClips/ClipTransport 调度` 零改动；`trackList` 为纯元数据容器。
- 迁移：`validateProject` 见无 `trackList` 且有 clips → 建 trk1 并给全部 clip 补 `trackId`；载入零体验变化。
- 轨上限建议 4（移动端纵向空间硬约束）；`gain` 线性 0..2（与现 trackGain 域一致）；solo 不做（P2 再议，`effectiveMute` 语义照抄 lightmix）。

**引擎（audio-clips.js）**：
- `computeOverlaps/applyAutoCrossfades/pruneAutoCrossfades/rippleDeleteClips/effectiveRegions` 增加 trackId 作用域（同轨才参与重叠/波纹；跨轨叠放=混音叠加，不触发交叉淡化——与 Audition 语义一致）；
- `ClipTransport`：master 之下建 `trackGains: Map(trackId→GainNode)`，`scheduleClip` 改接 `clipGain→trackGain→master`；`setTrackGain(trackId,g)/setTrackMuted(trackId,m)`。

**渲染与交互（timeline.js）**：
- 音乐模式（§3.2）下 lane 从 1 条变 N 条堆叠，每轨独立高度（存 `track.height`）；轨表头列（120px）逐轨：名称/音量滑杆/静音/删除（空轨才可删）；
- 「＋ 音轨」按钮（轨表头列尾）；clip 拖拽支持**纵向跨轨**（pointermove y 命中轨 → drag.trackId 更新，松手改 `clip.trackId`）；跨轨拖动时磁吸候选保持时间域不变；
- `tl-head` 单表头改造为轨表头列容器；简单态（编舞模式）恒为「trk1 单行 26px」，多轨内容在简单态折叠呈示为「N 轨」徽标。

**与既有联动**：按队形段自动切逐轨执行；媒体库拖入=落点+当前选中轨；导出含乐 v2 不变（clips 已随项目走）。

|---|---|
| 工作量 | **M–L**（模型/迁移 S；引擎作用域 M；渲染+跨轨拖拽 M；回归面大） |

### 3.3 节拍体系裁定（反馈 #3）—— P0 裁定 + P1 可选演进

**裁定（基于 §2 实证）**：
1. **剪辑/音乐层：全面秒制，维持现状**——clip 模型、调度、trim/分割/淡化已全秒制且实证免疫节奏型（§2.2）；**明确放弃「clip 的节拍绑定」，永不引入**。仅有的两处拍耦合输入修正：
   - clip 微移 Shift 网格：保留「整拍步进」但标注「按标称 BPM」；磁吸候选补「秒网格 0.5/0.1s」（音乐模式默认秒网格，编舞模式默认拍网格）；
   - 「按队形段自动切」在非恒速曲上的切点偏移属拍模型误差——加载入体检提示（下条）。
2. **队形层：保留拍值（八拍是编舞领域母语），不采用全面秒制（方案 B 否决，见 §2.3）**；拍值继续是 blocks/tags 的存储与编辑单位。
3. **恒定 BPM 假设显性化（P0 核心动作——把隐性缺陷变显性契约）**：
   - BPM 行 title 与说明书补：「对齐基于全曲恒定 BPM；现场版/渐快渐慢等变速曲拍线会漂移」；
   - **载入体检（建议 P1，代码面小）**：载入音乐后对已解码 buffer 做 onset 间隔一致性粗检（IOI 中位数偏差 > 阈值 → toast「此曲可能非恒定 BPM，拍线/数拍仅供参考」+ BPM 行警示点）；实现面=复用已有解码与包络，无新依赖；
   - 缺陷报告建档：本实证作为「已知限制」条目入 `music-editing-defects.md` 口径。
4. **无节奏型/变速曲的降级策略（P0）**：
   - 尺规秒刻度开关（音乐模式默认秒刻度、编舞模式默认拍刻度）——lightmix `NICE_STEPS/majorStep` 纯函数可直接移植（65 行级）；
   - 块时长栏双单位：徽标已是「16拍·8s」双呈示；± 步进增加「按住 Alt = ±0.5s」秒步进（实现为拍换算后写回，数据模型不动）；
   - 节拍器/数拍：体检判定非恒速时提示「节拍器可能不合拍」；数拍保留（走表不依赖音乐内容，本来就是「给演员听的入场」）。
5. **P1 可选演进：方案 C 有限节奏图**——`audio.tempoMap: [{fromBeat, bpm}]`，`beatToSec/secToBeat` 分段线性化（46 个调用点签名不变），4 处 `spb` 直调改 `spbAt(beat)`；恒速曲 tempoMap 缺省=现状零迁移。**触发条件（需用户拍板）**：确认真实曲目库中「分段恒速曲」（如现场版两段式）占比可观、且愿意为 tempoMap 编辑 UI 付出一轮工作量。渐变速（rit./accel. 连续变化）仍不在解内——那需要 B 或时间伸缩，超出本轮。

| 项 | 值 |
|---|---|
| 工作量 | 裁定+文档化 **S**；显性化提示+秒刻度开关+Alt 秒步进 **S–M**；载入体检 **S**（P1）；节奏图 C **M**（P1，需拍板） |
| 风险 | 显性化提示的误报（强节奏但 IOI 方差大的曲风）→ 体检阈值保守、文案「可能」；节奏图编辑 UI 的心智负担 → 先只做「导入段落表生成 tempoMap」（见 §3.4 story 6）不做手编 |
| 依赖 | 无；C 依赖用户拍板 |
| 验收（IR） | IR-B1 恒速曲全链路回归绿（对齐/数拍/节拍器/自动切与 v0.9.20 一致）；IR-B2 变速曲载入 → 呈现已知限制提示（或体检 toast）；IR-B3 秒刻度开关两模式默认值正确、切换即刷；IR-B4 Alt 秒步进写回后拍徽标与秒数一致；IR-B5（若 C 立项）双段 tempoMap 下：tag/块边界/节拍器/自动切全部按分段换算，§2.1 同款探针偏移归零（复跑 `r2-a` 断言 offsetSec≤60ms） |

### 3.6 多选弹框一致性（反馈 #6）—— P0

**设计**：单人与多选收敛为一个 `SelectionMenu`（同一组件骨架，单人=N=1 特例），分层构成：

```
┌──────────────────────────────┐
│ 已选 3 人（或：舞者 · M1）      │  ← 标题：N 与成员短语（>4 人折叠「等 N 人」）
├──────────────────────────────┤
│ 朝向 ▸  面向观众 / 面向圆心     │  ← 群体语义：对整个 selection 生效（N=1 同样可用）
│ 存为编组                       │  ← 群体：capture 当前 selection（与 Ctrl+N 同语义）
│ 合并为单元（仅 N=2 且无合并）   │  ← 既有 mkMultiMergeBtn 平移
│ 取消合并（仅涉合并单元时）      │  ← 既有 mkMultiUntieBtn 平移
│ 均布（仅 N≥3；右键切方向同工具栏）│ ← 群体：新增浮窗入口（复用 shapes.distributeAxis）
├──────────────────────────────┤
│ 移出队形                       │  ← 新增（=Del 键语义，浮窗此前无入口；单人/群体同项）
│ 删除所选（N 人）／删除（N=1）    │  ← 危险区红色，恒在末位
│ ✕                             │  ← 取消，恒在底
└──────────────────────────────┘
```

**群体语义约定**：所有操作项作用域=「单元原子展开后的 selection」（既有 `expandedIds` 不变）；「朝向」对每人写 `facing`（复用 `shapes.faceAll` 带 selection）；「均布」复用工具栏逻辑；单人菜单自动退化（合并/均布条件不满足即隐藏对应项）——**结构恒一致，可见项按条件显隐**，而非两套代码。

**不做进浮窗的**（留工具栏，避免浮窗过长）：镜像/旋转/生成器/换位（低频或需上下文）。

| 项 | 值 |
|---|---|
| 工作量 | **S–M**（重构 `showUnitMenu` 分支为条件显隐单骨架；新增 3 个群体动作接线均为既有模型函数调用） |
| 风险 | 低；注意 `payload.mode` 既有四态（merge/unit/context/multi）有单测与 L2 仪器依赖——保留对外 payload 协议，仅重构内部按钮构成 |
| 依赖 | 无 |
| 验收（IR） | IR-S1 单人长按/右键：与多选同骨架，可见项=朝向/存编组/移出队形/删除；IR-S2 多选 3 人：朝向生效于 3 人、均布可选、存编组 N=3；IR-S3 多选 2 人未合并：合并为单元可用且与工具栏同语义；IR-S4 涉合并单元多选：取消合并可见、拆后成员移出选择（既有语义保持）；IR-S5 触摸长按与鼠标右键构成一致；IR-S6 gesture 四态 payload 单测与 L2 仪器回归绿 |

## 5. 需用户拍板的决策点

1. **多轨排期与形态**（§3.1）：确认「扁平 audioClips + trackId + trackList」路线与 4 轨上限；是否需要 solo（建议 P2）。
2. **节拍裁定确认**（§3.3）：接受「队形层保留拍制 + 恒定 BPM 显性化」；**是否立节奏图 C**——取决于真实曲目库中变速/分段恒速曲的占比（立则批次 2 后插队）。
3. **音乐模式下舞台区呈现**（§3.2）：方案默认「保持当前画面、播放照常联动」；备选「舞台收窄给时间轴让空间」（移动端收益大）或「全屏化」（P2）。
4. **多选浮窗操作集取舍**（§3.6）：默认进浮窗=朝向/存编组/合并族/均布/移出队形/删除；镜像/旋转/换位留工具栏——请确认或增删。
5. **图标范围与风格**（§3.5）：线性 stroke 风格确认；库空态 💃 是否保留为插画（默认：空态保留插画图，仅 chrome 按钮换 SVG）；播放条是否转纯图标（默认转）。
6. **体检提示的容忍度**（§3.3）：非恒速粗检存在误报可能——「可能非恒定 BPM」软提示（默认）vs 强提示（阻断式不可取，建议不采用）。
